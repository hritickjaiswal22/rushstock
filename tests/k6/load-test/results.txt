## Bugs found by the load test

### Bug 1 — `SELECT … FOR UPDATE` serialized the reserve path

**Symptom:** 68/100 successes, requests taking up to 15 seconds.
**Root cause:** The reserve transaction locked the sale row with `FOR UPDATE`
before reading it — but the reserve path only *reads* the sale (it does not
modify stock; that happens at confirm). The lock serialized every concurrent
reserve into a queue.
**Fix:** Removed `FOR UPDATE` from `postHold` in `src/services/holds.ts`.
**Result:** p95 latency dropped ~25%.

### Bug 2 — Prisma connection pool exhausted under 500 VUs

**Symptom:** 10–16 requests returning `500`, with the server log showing
`P2028: Transaction API error: Unable to start a transaction in the given time.`
**Root cause:** Prisma's default `pg` pool size is ~`num_cpus × 2 + 1`, roughly
9 on a laptop. With 500 concurrent virtual users, requests queued for a
connection and exceeded Prisma's 2-second `maxWait`.
**Fix:** Provided an explicit `pg.Pool` with `max: 50` to the Prisma adapter in
`src/lib/prisma.ts`.
**Result:** Zero `500`s. All three thresholds green.
